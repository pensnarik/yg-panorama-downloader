# Каталог панорам и происхождение дат

## Обновление существующей БД

Остановите сервер и монитор на время обновления. Если V003 ещё не применена,
выполните её от администратора PostgreSQL:

```bash
sudo -u postgres psql -d panoramas -v ON_ERROR_STOP=1 --single-transaction \
  -f db/migrations/V003__Panorama_catalog.sql
```

Затем примените V004 (если она ещё не применена):

```bash
psql -X -h localhost -U panorama_admin -d panoramas -v ON_ERROR_STOP=1 --single-transaction \
  -f db/migrations/V004__Panorama_payload.sql
.venv/bin/python -m panorama_archive.backfill
```

V004 переносит все JSONB-поля основной таблицы в `aa.panorama_payload`
и удаляет прежние колонки в одной транзакции. Для уже заполненного каталога
повторный backfill не требуется. Код сервера и экспортера требует V004.

V001 и V002 должны быть уже применены; повторно их выполнять не нужно.
Команда backfill выполняется в транзакции, её можно запускать повторно.
Она обрабатывает все логи, затем локальные `map/*/metadata.json`, затем
сохранённые ответы из `aa.yandex_panorama_metadata`. Локальные файлы позволяют
восстановить записи, полного ответа для которых уже нет в БД.
Другой каталог задаётся через `--library /путь/к/map`.

После заполнения перезапустите сервер и монитор. Просмотрщик работает без БД.
Автоматический экспорт манифестов и подписи новых склеенных JPEG используют каталог;
уже созданные JPEG автоматически не переписываются.

## Структура

- `aa.panorama`: одна запись на `(provider, external_id)`. `external_id` — ID
  изображения в каталоге тайлов; `panorama_id` — отдельный ID провайдера.
  Координаты, высота, название, размер тайла, ориентация проекции, направление
  и углы обзора представлены отдельными типизированными столбцами.
- `shooting_year`, `shooting_month`, `shooting_day`, `date_precision`,
  `date_source`, `date_conflict`: дата с явной точностью и происхождением.
- `time_candidate`, `time_source`: предполагаемое время из ID, **не подтверждённое
  время съёмки**. `provider_timestamp`, `legacy_timestamp`, `page_date` сохраняют
  исходные временные свидетельства раздельно.
- `client_observed_at`: непроверенные часы браузера. `received_at` — часы сервера
  при заполнении каталога; при backfill это время переноса, а не старого перехвата.
  `first_seen_at` восстанавливается по самому раннему журналу, где это возможно.
- `aa.panorama_payload`: объёмные JSONB-поля `projection`, `images`, `default_view`,
  `annotation`, `raw_response`, `capture_envelope`, `latest_observation`. Связь
  один к одному по `(provider, external_id)`, удаление вместе с панорамой.
- `aa.panorama_level`: отдельная строка на каждый уровень детализации с шириной,
  высотой и исходным описанием уровня.
- `aa.panorama_capture`: история различных исходных ответов с SHA-256 содержимого,
  без использования `capturedAt` как версии. Повторы не размножают одинаковый ответ.

Изменяемые вложенные структуры проекции, изображений, вида и аннотаций хранятся
в разобранном JSONB в `aa.panorama_payload`. `raw_response` и `capture_envelope` сохраняют полный ответ
и оболочку, включая неизвестные будущие поля, граф соседей, подписи и историю.
Последнее наблюдение страницы хранится в `latest_observation`; новые полные
наблюдения также сохраняются в `panorama_log_meta`. Старые логи не удаляются.

Ответ API имеет приоритет над наблюдением DOM при обновлении каталога.
Год не заменяет ранее известный месяц или день. Сервер обновляет каталог
в одной транзакции со старым журналом и таблицей метаданных. Одинаковый ответ
идемпотентен независимо от изменения часов клиента. История не позволяет
автоматически определить, какой различающийся ответ провайдера новее;
текущим считается последний принятый, а не имеющий максимальный `capturedAt`.

## Что обнаружено в существующих данных

В `background.js` поле `capturedAt` создаётся через `new Date().toISOString()`
при получении HTTP-ответа. Это наше поле, не свидетельство времени съёмки API.
Пример `Z7lngTdIrFox`:

| Источник | Значение UTC | Использование |
|---|---|---|
| `capturedAt` | 23.09.2026 17:53:32 | Перехват метаданных, не съёмка |
| `Data.timestamp = 1757937600` | 15.09.2025 12:00:00 | Дата API, без доверия к времени суток |
| Суффикс ID `1757904742` | 15.09.2025 02:52:22 | Предположение о времени, явно отмеченное в UI |

У соседних панорам API timestamp одинаков, а ID идут с интервалами в несколько
секунд. Это поддерживает гипотезу времени съёмки в ID, но не доказывает её.
В просмотрщике не выдаём время из ID за подтверждённое. Признак конфликта
учитывает расхождение календарных дат более суток и несовпадение года из DOM.
Для Google дата из текста страницы сохраняет точность года/месяца; часы неизвестны.

## Проверки

Обычные тесты выполняются без сети и БД. Для интеграционных проверок SQL:

```bash
PANORAMA_DATABASE_TESTS=1 .venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

Интеграционные тесты используют `pg_temp` и существующий тип провайдера из V001,
не меняют рабочие таблицы, проверяют типы, повторную запись, историю, приоритет
источников и откат транзакции. Их можно выполнить до применения V003.

## Адрес

Непустое имя API имеет приоритет, но пустое значение не стирает уже известный
адрес. Наблюдение `extractView()` заполняет адрес, если API его не предоставил.
Backfill также восстанавливает отсутствующие адреса из последнего непустого
`panorama_log.view_name`. Просмотрщик получает адрес каталога отдельным полем
`catalogTitle` в локальном манифесте, сохраняя исходный ответ API без изменений.
